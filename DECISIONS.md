# Decisions

One line each on *why*, so future-me (or an interviewer) doesn't have to reconstruct it.

1. **Approval gate — auto-approve, gate still fires.** `ApprovalGate.policy` is `"auto"` by default; every `run_tests` call is approved but emits a real `approval_gate` trace event. Flip to `"block"` for production. See [`harness/tools/base.py`](harness/tools/base.py).
2. **Rate limiting — per-IP + global daily cap, fixed kata set.** `POST /solve` only accepts known `kata_id`s (no user-supplied problems), which removes the biggest injection surface. See `_check_rate_limit` in [`api/main.py`](api/main.py). Localhost/loopback (`127.0.0.1`, `::1`, `testclient`) is exempted — the limit exists to protect a public deployment's free-tier LLM quota, not to throttle the person developing against their own machine; it fires exactly as designed for any other IP.
3. **Provider — `OpenAICompatProvider`, OpenRouter free tier default.** One class covers OpenRouter/Groq/Together/DeepSeek/Gemini's OpenAI-compat endpoint via config. `FakeProvider` is the automatic fallback when no `OPENROUTER_API_KEY` is set, so the demo runs with zero setup — see [`harness/providers/fake.py`](harness/providers/fake.py). It's a real `LLMProvider`, not a test mock: it scripts `binary_search` to fail on attempt 1 (off-by-one) and pass on attempt 2, which is how the retry story is demoable without hitting a network API.
   - **Item 1 (verified):** the API key alone suffices — only `Authorization: Bearer <key>` is required; OpenRouter routes to the configured free model. `HTTP-Referer`/`X-Title` are optional ranking headers, sent but not needed.
   - **Item 2 — safety-model retry:** OpenRouter intermittently routes a free request to a moderation model that returns a bare `User Safety: safe` verdict. `looks_like_safety_verdict()` detects that shape and the provider re-issues the call (default 3 retries) so a real model answers, counting re-routes on `Completion.safety_retries` → traced as `safety_retries` and shown in the UI. If every retry still hits the safety model, the last verdict is returned (not swallowed) so the failure is visible.

3a. **Animation pacing (UI, items 3-4).** The flow is event-driven from SSE but played through an async action queue with a minimum dwell per stage, so a <100ms fake run is still watchable and a slow real LLM call simply holds the "thinking" state until its `ok` event. `tween()` advances on `requestAnimationFrame` *and* a fallback timer, so the animation still completes if the user backgrounds the tab (rAF pauses) instead of stalling mid-travel.
4. **Web search tool — removed.** Weakly motivated for katas; not built.
5. **Oracle precedence.** `VerificationReport.passed` is exactly `oracle_passed`; there's no advisory-failure path wired up yet in Phase 1 (that's the Tester subagent in Phase 2), but the field exists on the dataclass already so Phase 2 doesn't need a schema change.
6. **Sandbox — `SubprocessSandbox` only in Phase 1.** `SandboxExecutor` is an ABC so `DockerSandbox` slots in later without touching callers. Isolation is `resource.setrlimit` (CPU + address space) plus a hard `subprocess.run(timeout=...)` wall-clock kill — see [`harness/sandbox/executor.py`](harness/sandbox/executor.py). `RLIMIT_AS` isn't always enforced on macOS; the wall-clock timeout is the real backstop cross-platform (verified in [`tests/test_sandbox.py`](tests/test_sandbox.py)).
7. **Trace event field names follow OTel `gen_ai.*` spelling** where an equivalent exists (`gen_ai.completion`, `gen_ai.tool`, `gen_ai.usage.input_tokens`), so Phase 3's "full OTel conformance" is a rename, not a rewrite.
8. **Name — Glassbox** (repo `glassbox-harness`). The project's premise is making the harness transparent — the opposite of a black box.

## Phase 2 decisions

9. **Strategy pattern for orchestration, not a replacement.** `Orchestrator` (Phase 1, single-agent tool-calling loop) and `MultiAgentOrchestrator` (Phase 2, Planner→Coder→Tester) both exist; `POST /solve {mode}` picks one. Same reasoning as `SandboxExecutor`'s two strategies (Decision #6) — the single-agent story stays fully intact and testable rather than being torn out. The shared LLM↔tool turn-taking (`ToolCallLoop`, extracted from `Orchestrator._attempt`) is reused by the Coder subagent instead of being reimplemented — see [`harness/tool_loop.py`](harness/tool_loop.py).
10. **Escalation policy — replan after 2 consecutive Coder failures.** The plan explicitly left this as an open design call (§4.2). Attempt 1 always runs the Planner; each subsequent failed attempt re-runs only Coder+Tester with structured failure feedback, keeping the existing plan; after 2 consecutive failures the Planner re-runs with the failure history to produce a revised plan. Chosen over "replan every attempt" (wasteful — most fixes are local) and "never replan" (a genuinely wrong plan would loop forever). See `MultiAgentOrchestrator._attempt` in [`harness/orchestrator_multi.py`](harness/orchestrator_multi.py).
11. **Tester owns the oracle call, not the Coder.** In the single-agent loop the model's own `run_tests` call can satisfy oracle precedence (Decision #5) if it matches the final code. In multi-agent mode the Coder's `ToolCallLoop` still has `run_tests` available for self-checking, but the *authoritative* pass/fail always comes from the Tester's own call — this keeps the subagent boundary honest (Coder writes, Tester verifies) rather than letting the Coder's optional self-check silently become authoritative.
12. **Tester's edge cases are inputs only, not input/expected pairs.** The Tester subagent doesn't know the correct output for a case it invents — only the oracle's fixed test set has verified expected values. So a Tester-proposed edge case only becomes an `advisory_failures` entry if the code crashes or times out on it, never on a value mismatch it can't verify. This is what makes oracle precedence (Decision #5) actually safe to wire up in Phase 2 — advisory findings are real signal (the code broke) without ever risking a false "fail" from a guessed expected value.
13. **Context budget uses `len(text)//4`, not a real tokenizer.** No dependency added for a budget *estimate* — see ground rule "stdlib first, add a dependency only when stdlib genuinely can't do it." `ContextManager` keeps the system+problem message and the most recent attempt's code/failure verbatim, collapses older attempts to one-line summaries, and drops oldest summaries first if still over budget — logged to the trace as a `context` event so the "stays under a fixed token budget" exit criterion is provable, not just asserted.
14. **Skills use hand-rolled frontmatter, not PyYAML.** `name:`/`description:`/`triggers:` between two `---` lines is simple enough to parse with `str.partition(":")` — same stdlib-first reasoning as #13. See [`harness/skills/loader.py`](harness/skills/loader.py).
15. **Durable memory is SQLite only (Phase 3a) — Postgres/Supabase (3b) is out of scope here.** The plan splits P14 into 3a/3b explicitly; Railway's disk being ephemeral only matters for an actual Railway deployment, which this pass doesn't include. Noted here rather than silently limited. The recall stretch (§5.2, "optional... be honest if skipped") **is implemented**: `AttemptStore.recent_failure_hint()` surfaces the most recent same-category failure into the Planner's first-attempt prompt — real memory, not just a log.
16. **Cost estimation is a real (if currently all-zero) computation, not a hardcoded 0.0.** `harness/costs.py` has a price-per-1K-token table; every deployed model in this repo happens to be free, but the function looks the model up and multiplies rather than returning a constant, so a paid model slots in via one table row — "compute it even at $0 is the production habit" (plan §5.3).
17. **UI redesign (final): a fixed flowchart with real loop-back edges, not a ring or per-attempt lanes.** Two earlier iterations both missed the actual ask. First, a ring around a central model core looped every attempt through the same circular positions — a retry looked visually identical to the first attempt, so *which* retry was running, and how many there'd been, wasn't legible (user feedback: "we can see any kind of loop and all"). Second, a "one row per attempt" redesign fixed legibility but flattened the loop into repeated boxes instead of showing it as a loop (user feedback: "single lane highway, stupid"). The design that actually matches the ask (`ui/app.js::buildBoard`/`computeLayout`): ONE persistent flowchart per run, vertical, not per-attempt — a retry is a real curved edge from Oracle back up to the top (purple), a same-plan retry (Tester failed, no replan) is a shorter edge straight back to Coder (blue), and the model being asked again mid-attempt (tool-calling round, Tester's edge-case sweep) is a third edge back up to Provider (amber). Each loop edge carries a live counter badge (`retry ×2`, `model asked again ×3`) instead of spawning a new node. Every event is synchronously tagged with its attempt number and (in multi-agent mode) subagent role the instant it arrives (`tagEvent()`), independent of the animation queue's pacing — several event kinds (`approval_gate`, `gen_ai.tool`, `sandbox_exec`) don't carry `attempt_no` in their own attrs, so this tagging is what lets the story feed and the click-to-inspect modal (which now shows every occurrence across the whole run, most recent first, each labeled by attempt) attribute correctly.
18a. **Story feed replaces a raw event log as the primary UI for the Live Trace panel.** Explicit ask: the UX should make it legible *why* a small quantized model can land a hard problem — not just that it eventually passed. `narrate()` converts a curated subset of trace events (attempt start/retry, subagent verdicts, the harness's authoritative check vs. the model's own self-check, oracle pass/fail with reason, skill loads, memory recalls, safety-model reroutes) into one plain-English sentence each, grouped by attempt with the same collapse-on-next-attempt behavior as before. This is deliberately lossy — most raw events (individual approval gates, sandbox spin-ups) don't narrate — so a "show raw trace (N)" toggle per attempt group still exposes the complete underlying event list for anyone who wants it, without it being the default view.

## Phase 4 decisions — dynamic problems

19. **The fixed kata set is gone; problems are fetched at runtime.** `POST /solve` takes a `problem_ref` — a LeetCode number/slug/URL, a curated kata id, or pasted problem text — instead of one of seven hardcoded ids. `ProblemSource` is an ABC with three implementations chosen by which one recognizes the reference (same strategy shape as `SandboxExecutor`, Decision #6): `LeetCodeSource` (GraphQL), `PastedTextSource` (always works), `CuratedSource` (the original 7 katas, kept because they're the only problems that run with no network and no API key, and they're what most tests exercise). See [`harness/problems/`](harness/problems/).

20. **Extraction is deterministic-first, LLM-fallback — not the other way round.** The extraction *is* the oracle: anything hallucinated there silently becomes the definition of "correct". LeetCode publishes the python3 starter snippet (exact signature + whether it's a function or a design problem) and the ground-truth answer for every worked example, so both are parsed mechanically ([`problems/signature.py`](harness/problems/signature.py), [`problems/examples.py`](harness/problems/examples.py)). Measured against live problems 1, 20, 42 and 295 that covers everything with **no model call at all**. The LLM runs only when deterministic parsing comes up short (pasted text, unusual layouts), and the route taken is recorded as `extraction_method` and shown in the UI — "parsed from the statement" and "written by the model" are different trust levels and shouldn't look the same.

21. **Complexity budget is a lookup table, not a model call.** Mapping a constraint bound to an acceptable Big-O is the standard ~10^8-ops-per-second heuristic — a table, not a judgment ([`harness/complexity_budget.py`](harness/complexity_budget.py)). Keeping it deterministic means it can't be hallucinated and is trivially unit-testable. The hard part is reading the *right* number out of the constraints: `1 <= nums.length <= 10^5` is a size bound (drives complexity) while `-10^4 <= nums[i] <= 10^4` is a value bound (does not), so only size-shaped constraints are considered and `None` is returned rather than guessing. The budget is injected into the Coder's prompt and cross-checked against the pre-existing `analyze_complexity` tool, which finally has a real job.
    - **Bug worth recording:** LeetCode writes bounds as `10<sup>5</sup>`. Stripping tags naively yields `105`, silently turning n ≤ 100,000 into n ≤ 105 and handing the Coder a wildly wrong target. `html_to_text` emits `^` for `<sup>`; regression test in [`tests/test_problem_sources.py`](tests/test_problem_sources.py).

22. **Two oracle templates, because design problems aren't function calls.** LeetCode's "implement a class" problems (e.g. #295 MedianFinder) are graded by replaying an operation sequence — `[["MedianFinder","addNum"], [[],[1]]]` → `[null,null]` — which the function-call harness can't express at all. `TestOracle.build_harness` branches on `Problem.kind`. Float comparison is tolerant to 1e-5 (LeetCode explicitly accepts that for `findMedian`), with a guard so `True` never compares equal to `1.0`.

23. **The test-case authority ladder — how generated cases can fail a run without failing correct code.** This is the central correctness decision of Phase 4.

    | tier | source | authority |
    |---|---|---|
    | 1 | LeetCode examples / curated katas | **ground truth** (published answers) — sets pass/fail outright |
    | 2 | generated case that agrees with the code | no action |
    | 3 | generated case that **disagrees** | **Judge adjudicates** → `bad_test` (discard) · `real_bug` (hard failure + retry) · `uncertain` (advisory only) |
    | 4 | crash / timeout / constraint violation | always real — advisory, no judge needed |

    `VerificationReport.passed` is now *ground-truth cases pass **and** no generated case was judged `real_bug`*, which keeps Decision #5's oracle precedence intact while letting the generated tier matter.

24. **The Judge never manufactures ground truth — it only adjudicates a disagreement.** Asking an LLM "what is the correct output for this input?" is asking it to re-solve the problem; it will be wrong precisely on the hard problems this harness exists to showcase, and a wrong judge fails *correct* code. So it is never consulted about a tier-1 case (those answers are already published) and never when things agree. It sees one concrete conflict — statement, input, what the code returned, what the invented test claimed — and rules which side is wrong, with a genuine `uncertain` escape hatch so it isn't forced into a coin flip. Silence, garbage, or an unparseable verdict all default to `uncertain`, never `real_bug`. Every verdict is traced and rendered. See [`harness/subagents/judge.py`](harness/subagents/judge.py) and `tests/test_judge.py`.

25. **Generated inputs are filtered deterministically before they can reach the oracle.** A hallucinated case that violates the stated constraints (or proposes a 10-million-element array) is dropped by `testgen.filter_cases` with a recorded reason, not quietly executed — otherwise an invented input could blow the sandbox's memory limit or become part of the definition of correct. Arity, design-case shape, `max_n` and an absolute size ceiling are all checked.

26. **Fetching is allowlisted and treated as untrusted data (revises Decision #2).** Decision #2 removed the injection surface by refusing user-supplied problems; Phase 4 deliberately reopens it, so the mitigations are explicit: an `ALLOWED_HOSTS` allowlist (leetcode.com only) enforced on every URL, so `/solve` can't be turned into an SSRF proxy for internal addresses (tested against cloud-metadata and localhost URLs); fetched statements are inserted into prompts inside explicit delimiters and labelled untrusted; and the extractor's output is schema-constrained to data fields. Fetching happens in the harness process — a trusted, allowlisted action — never inside the sandbox.

26a. **Correction — the sandbox was never actually network-less.** Decision #6 and the code comment in `sandbox/executor.py` both claimed `env={"PATH": ...}` meant "no network". That was wrong: clearing the environment only strips inherited *proxy config*; it does nothing to outbound sockets. Verified during Phase 4 — a `urllib` call from inside the sandbox reached leetcode.com and came back with a 403. A `_NETWORK_GUARD` preamble is now prepended to every sandboxed script, neutering `socket.socket`, `create_connection`, `create_server` and `getaddrinfo`. Stated honestly: this is a **guardrail, not a security boundary** — it stops accidental and casual network use by in-process Python, which matches the real risk profile (LLM-written solutions to coding problems), but code that deliberately wants out can reimport the C module or spawn a subprocess. A genuine boundary needs OS-level isolation: a network namespace on Linux, or `DockerSandbox` with `--network none`. Regression tests in [`tests/test_sandbox.py`](tests/test_sandbox.py).

27. **Metrics are pure aggregation over existing spans.** `harness/metrics.py` adds no instrumentation; it rolls up what the Tracer already emits into wall time, the model-vs-harness time split, tokens and cost per agent, and phase timings. The split is the point: it separates time that scales with whichever model you plug in from time the harness itself costs, which is what makes "a small model plus a real harness" legible as a claim rather than a slogan.
